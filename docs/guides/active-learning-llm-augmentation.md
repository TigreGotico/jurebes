# LLM-driven data augmentation with jurebes as the oracle

A classical-ML classifier is a cheap, fast, label-aware filter for synthetic data generated by a language model. Jurebes is well-suited to this role: `IntentClassifier` retrains in milliseconds, exposes calibrated `predict_proba`, and ships a confusion-matrix in every `RunResult`.

This guide shows the canonical three-bucket loop and the jurebes APIs it relies on. A runnable implementation lives in [`examples/llm_augmentation/`](../../examples/llm_augmentation/).

## The pattern

For each round:

1. **Generate.** Ask the LLM for `N` paraphrases per intent, with a few seed examples as context.
2. **Score.** For every paraphrase, get jurebes's top prediction and the confidence it assigns to the **requested** intent (not just the top one).
3. **Bucket.**

   | bucket | condition | action |
   |---|---|---|
   | SKIP    | predicted = requested, confidence > threshold | drop — model already knows |
   | HARD    | predicted = requested, confidence ≤ threshold | keep — uncertainty signal |
   | SUSPECT | predicted ≠ requested                          | judge before keeping |

4. **Judge.** SUSPECT samples might be LLM intent drift (corrupt) or genuinely-confusing boundary cases (valuable). A second LLM call ("does this utterance preserve the intent X? yes/no") resolves the ambiguity. Without a judge, dropping SUSPECT is safer than keeping it.
5. **Retrain.** Fit jurebes on the original samples plus HARD plus judge-approved SUSPECT.
6. **Evaluate.** Score on a **frozen, never-regenerated** held-out set. Stop when macro-F1 plateaus.

## Why three buckets, not two

The naive "keep only wrong predictions" loop has a silent failure mode: the LLM frequently drifts off the requested intent (you ask for `play_song` paraphrases, it produces a `play_video` utterance). Adding those as `play_song` training data **corrupts the dataset**. The judge step rejects them.

The HARD bucket is where the real signal lives — those are the near-boundary examples that move the decision surface. If you only kept SUSPECT samples, you'd never see the bucket where the gradient lives.

## The jurebes APIs you need

### `predict_proba` for the confidence cut

```python
ranked = clf.predict_proba(utterance)
top = ranked[0]
conf_for_requested = next(
    (r.confidence for r in ranked if r.intent == requested_intent),
    0.0,
)
```

`predict_proba` always returns calibrated probabilities — even for baselines that lack native `predict_proba` (LinearSVC, SGDClassifier with hinge loss), jurebes auto-wraps with `CalibratedClassifierCV`. See [`docs/theory/calibration.md`](../theory/calibration.md).

### `fit` for the cheap retrain

```python
clf = IntentClassifier(BASELINES.build("logreg"))
for intent, samples in growing_samples.items():
    clf.add_intent(intent, samples)
clf.fit()
```

`logreg` on a few hundred samples fits in tens of milliseconds. `linear_svc_char` retrains in a few hundred milliseconds. Either is fast enough to run inside the loop without batching.

### `confusion_matrix` for targeted augmentation

```python
from jurebes.benchmark import cross_validate

result = cross_validate("logreg", X, y, k=3)
cm = result.confusion_matrix
labels = result.labels
```

The most-confused intent pair `(labels[i], labels[j])` where `cm[i][j]` is large tells you which generation prompt is highest-value: ask the LLM specifically to produce utterances that disambiguate `labels[i]` from `labels[j]`. This is **hard-negative mining** and works very well on banking/news/customer-service intents that share vocabulary.

### `compare()` for measuring round-to-round delta

```python
from jurebes.benchmark import compare, to_markdown

result = compare(["logreg", "linear_svc", "nb_multinomial"],
                 eval_X, eval_y, k=3)
print(to_markdown(result, sort_by="macro_f1"))
```

Drop into the loop's end-of-round step to spot regressions across multiple baselines, not just the one driving the loop.

## Pitfalls

### Reflection — evaluating on regenerated data

If you regenerate the eval set every round with the same LLM, you measure progress against your own reflection. The held-out set must be fixed up-front or sourced from real users.

### LLM-distribution overfit

The loop ends with a classifier excellent at the LLM's phrasing patterns. That is not the same as excellent at real users. Hold-out should be real-user data when possible. If only LLM data exists, set aside a frozen subset before the loop begins and never touch it.

### Confidence-threshold sensitivity

The HARD bucket boundary (`hard_conf_max`, default `0.6`) is a hyperparameter. Too low and you skip useful samples; too high and you accept samples the model already knows. Sweep this in the first round if the loop plateaus without learning.

### When NOT to use this loop

- Tiny intent sets (< 5 intents) — manual seed expansion is faster.
- Hot domains (intent inventory changes daily) — the loop's value is in deepening fixed intents, not chasing new ones.
- Datasets where slot extraction is the harder problem — augmenting intent samples doesn't directly help the IOB tagger. Use template grammars + [`expand_slots`](../reference/datasets.md#bracket-expansion-helpers) instead.
